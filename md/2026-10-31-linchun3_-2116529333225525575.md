# Stop Fixing Your Coding Agents. Fix Your Repo.

## Post

I've been building apps with coding agents for a while now, and I'm increasingly convinced that every repo needs a standard engineering setup designed for agents.
The goal is simple: different engineers, each with their own agents, contributing to the same codebase without sacrificing quality or velocity.
I want agents to trip less, catch their own mistakes, and leave behind code that future agents can actually maintain.
Here's what I'm using or exploring.
1. Make correctness verifiable
Don't rely on prompts, skills, or AGENTS.md to enforce engineering standards. Encode them into checks that agents can run.
My Python stack:
ty: Catch type errors before runtime.
Ruff: Enforce consistent formatting and linting without wasting tokens on style.
import-linter: Enforce architectural boundaries and prevent unwanted dependencies.
pytest + Hypothesis: Verify behavior and invariants across generated inputs, not just a handful of examples.
Example: an agent imports database code directly into business logic. The feature works, tests pass, but we've introduced coupling that makes future changes harder.
With import-linter, that dependency fails a predefined contract. The agent has to fix it.
Same with typing. Catch a mismatch before runtime instead of wasting another iteration debugging it.
I care a lot about deep modules with simple interfaces. Tools can't guarantee good abstractions, but they can enforce the boundaries we've established.
The idea is to make the correct way of writing code the easiest way.
 
2. Make feedback fast and reproducible
Agents should verify their changes locally, with the same tools and versions as everyone else.
My preferred setup:
mise: Pin tool versions and define standard tasks.
uv: Manage Python dependencies and environments.
hk: Run formatting, linting, and other checks through hooks.
Give every repo one entry point: mise run check.
The agent runs it, reads the failures, fixes them, and repeats before opening a PR.
No waiting for CI just to discover a lint error. No inconsistent tool versions between engineers. No unnecessary round trips.
Make tests deterministic too. Flaky tests waste iterations because agents can't tell real regressions from noise.
And when I say fast, I mean fast. If something newer does the same job faster and reliably, switch.
 
3. Make success independently evaluable
This is the part I haven't cracked.
Trust me, agents write some really bad tests.
I've seen them generate tons of unit tests that mock everything, assert implementation details, and barely test actual behavior.
Everything passes. The application is still broken.
What I want instead:
E2E tests: Verify complete user journeys. This should be our strongest acceptance signal.
Integration tests: Use real databases and services in isolated test environments. Avoid mocking by default.
Property-based tests (Hypothesis): Generate inputs to uncover edge cases and violations of invariants.
Mutation testing (mutmut): Check whether tests detect meaningful changes to the implementation.
Protected acceptance tests: Run trusted tests that agents cannot modify just to make themselves pass.
I'm not against unit tests. I just don't think we need hundreds of them.
Tests should be orthogonal. Each should catch a meaningful failure that the others don't.
For example, an agent writes 20 unit tests for an API endpoint, mocking the database. All pass, but the endpoint fails because the actual database schema doesn't match.
One integration test against a real test database could have caught that.
For AI applications, I also want two types of evals:
Capability evals: Define what new functionality should accomplish. Hillclimb until they pass.
Regression evals: Protect behavior we've already established. These should pass 100%.
Once a capability is reliable, promote its evals into the regression suite.
I still spend too much time correcting agent-written tests. Getting agents to write genuinely useful tests without human steering remains an open problem for me.
 
4. Give agents a safe environment
Developers should still be able to use .env files and their usual local tools without giving agents access to every credential.
What I'd like to standardize:
Isolated agent workspaces without real .env files or developer credentials.
Scrubbed environment variables and restricted network access.
Fake credentials and real test services for local verification.
Scoped credential brokers when authenticated access is necessary.
Gitleaks to catch secrets accidentally committed to Git.
Secret scanning detects leaks. It doesn't prevent an agent from reading secrets.
And telling an agent not to read .env isn't a security boundary.
Enforce access through the environment, not prompts.
 
Why I think this matters even as models improve
Agents use existing code as context. If your repo has poor abstractions, inconsistent patterns, and weak tests, agents tend to reproduce them.
Models tend towards the middle, and frankly, most codebases aren't great to begin with.
Better models might navigate the mess better, but that doesn't mean the next agent won't add to it.
I don't just want agents to write code faster. I want codebases that get easier for future agents to extend and maintain.
Fewer mistakes, fewer round trips, less token spend, and less human steering through corrective actions.
Have I proven any of this? Nope.
Some of these tools I've tried. Others are on my list to experiment with. Most of this is vibes based on countless hours building with agents and figuring out what seems to help.
One day I'll run proper evals: same model, same repo tasks, with and without these setups. Measure acceptance rates, regressions, iterations, tokens, and time.
Until then, my working hypothesis is simple:
The engineering environment is part of the agent's capability.
We spend a lot of time improving models and prompts. I think there's just as much value in making our repositories better environments for agents to work in.
