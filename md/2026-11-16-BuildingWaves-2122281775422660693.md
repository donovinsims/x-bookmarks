1. Make sure search engines can read your website

Start with the boring stuff. This is where one wrong setting can hide your whole site.

Run Technical SEO audit.

Give your agent this prompt:

Check whether search engines can reach, render and index our homepage, main product or service pages, and a sample blog post. Inspect robots.txt, meta robots, HTTP headers, status codes, canonical URLs and the rendered content. Rank sitewide blockers first. Show the evidence and proposed fix. Don't change the site yet.

Review the fixes. Have your agent implement the approved changes, then check the live pages again.

Here's what you want in place:

HTTPS: your main pages load securely, without certificate errors.

One preferred URL per page: HTTP, HTTPS, www and non-www versions don't create a pile of duplicates. Redirects, internal links and canonical tags agree on the main version.

Indexable public pages: no accidental noindex in the page or response headers.

Working pages: important URLs return 200, not errors or endless redirects.

Readable content: crawlers can render your page's actual text, not just a loading screen.

Clear page basics: a useful title, a clear main heading, logical subheadings and a relevant description.

A canonical tag tells search engines which URL you prefer when similar versions exist. It isn't a way to rescue a broken site.

Also: robots.txt controls crawling. It is not a password, and it isn't a reliable way to remove a page from search. Keep private content behind proper access controls. See the technical audit's crawling and indexing rules.

2. Build your blog structure BEFORE filling it

Your agent needs somewhere sensible to put the content.

Use your existing CMS if it does the job. Don't build a custom publishing system just to start SEO.

A simple structure might look like this:

/                         Homepage
/features/                Product features
/pricing/                 Pricing
/blog/                    Blog index
/blog/how-to-dictate/      One useful article
/about/                   Who is behind the business

These paths are examples, not magic ranking factors. A service business might need service pages. A shop needs useful category and product pages.

Build one good blog template with:

An editable title, description and stable URL.

A clear headline, author and honest publish/update dates.

Readable text, useful headings and images with meaningful alt text.

A next step that fits the article, such as trying the product or booking a call.

Links to relevant guides and product pages.

A canonical URL, suitable structured data and automatic sitemap inclusion when published.

Make sure people can find the posts from your blog index. If the index has multiple pages, older posts still need crawlable links. Google generally discovers links through real HTML anchors with an href, not buttons that only run JavaScript. See Google's link guidance.

Run Site content inventory, then Internal linking plan.

Give your agent this prompt:

Map our current pages and blog structure. Find posts with no internal links pointing to them, broken links and gaps in the blog template. Propose a simple structure we can maintain. Give exact source pages, destination URLs and useful link text. Don't create empty categories or duplicate pages.

Review one complete test post on desktop and mobile before using the template for everything.

3. Add your sitemap and JSON-LD schema

These are different jobs. You want both handled properly.

Your sitemap is your URL list

An XML sitemap lists pages you want search engines to discover. Most established CMS tools can generate and update it for you.

A common address is https://yoursite.com/sitemap.xml. Some sites use a sitemap index that links to several sitemaps.

Keep it clean. Include the main, indexable URLs. Exclude redirects, error pages, private pages and duplicate versions. Only change a page's lastmod date when its content actually changes.

Reference the sitemap in robots.txt and submit it to Google and Bing in step 5. A sitemap helps discovery. It doesn't force indexing. Google explains sitemaps here.

Run XML sitemap check.

Give your agent this prompt:

Check our sitemap against the pages we want indexed. Flag missing important URLs, redirected or broken URLs, noindex pages and misleading lastmod dates. Show the exact edits needed and verify that publishing a new post updates the sitemap.

Open the sitemap yourself and check a product page and a published post are listed.

Schema explains what the page contains

People often call this “JSON schema.” For SEO, the thing you usually want is Schema.org structured data written as JSON-LD.

That is a small block of code that describes the real content on a page: the business, an article, a product or a breadcrumb trail.

Use the types that fit. Organization can describe your business. Article or BlogPosting can describe a post. BreadcrumbList can describe a visible breadcrumb trail. Product or local-business markup belongs on the relevant pages.

Don't invent reviews, ratings or business details. Schema must match what visitors can see. It can help Google understand a page and support eligible rich results, but it doesn't guarantee them. See Google's structured data guide.

Run Schema markup.

Give your agent this prompt:

Inspect our homepage and blog template. Recommend suitable Schema.org types and draft JSON-LD using only verified facts from the pages. Check for duplicate markup from plugins. Validate with Schema.org's validator and Google's Rich Results Test where supported. Show errors and missing facts before implementation.

Approve the markup, then test the live URLs with the Schema Markup Validator and Rich Results Test.

4. Make the site work properly on a phone

“Responsive” has two meanings here. The layout should fit the screen. And the page should react quickly when someone uses it.

Test your homepage, main sales page and a blog post. A fast homepage doesn't prove your whole site is fast.

Start with these tools:

PageSpeed Insights for mobile and desktop reports.

Chrome DevTools for device-size checks, Lighthouse and performance debugging.

A real phone for menus, forms, buttons and the signup or checkout flow.

Search Console's Core Web Vitals report once your site has enough real-user data.

PageSpeed includes lab tests and, when available, real-user data. Use the lab test to find problems. Use the real-user data to judge the experience people actually get. A new site may not have enough data yet. That's not a pass or a fail. Google explains the difference here.

The three Core Web Vitals targets are:

LCP: 2.5 seconds or less. How quickly the main content appears.

INP: 200 milliseconds or less. How quickly the page responds to interactions.

CLS: 0.1 or less. How much the layout unexpectedly shifts.

These targets are assessed at the 75th percentile of visits. See the Core Web Vitals definitions.

Don't chase a perfect Lighthouse score while your signup button is broken.

Run Technical SEO audit with your speed reports.

Give your agent this prompt:

Check mobile layout and performance on our main page templates. Use PageSpeed Insights and test the real signup flow. Separate lab findings from real-user data. Find the biggest causes of slow loading, delayed interactions and layout shifts. Propose the smallest useful fixes and record a before/after check.

Approve fixes, then retest the same pages and conditions.

Common fixes include smaller images, reserved image dimensions, less unnecessary JavaScript, fewer third-party scripts, caching and better font loading. Fix what the report actually finds. Don't blindly install five speed plugins.

5. Register with Google AND Bing

Now connect the site to the search engines and start collecting data.

Google Search Console

Open Google Search Console and add your site.

Choose a Domain property if you can verify through DNS. It covers the domain's protocols and subdomains. Otherwise, use a URL-prefix property and one of its supported verification methods. Google's verification guide walks you through it.

Open Sitemaps and submit your sitemap URL.

Inspect your homepage and a key page with URL Inspection. Test the live URL and request indexing if needed.

Check back for indexing problems and search performance as data arrives.

Your DNS provider is usually where the domain was registered or where its DNS is managed. Keep the verification record in place after verification.

If a page isn't indexed, investigate the reported reason. Repeatedly pressing “Request indexing” isn't an SEO strategy. Use URL Inspection to understand the problem.

Bing Webmaster Tools

Open Bing Webmaster Tools.

Import your verified site from Search Console, or add and verify it manually.

Confirm that the sitemap was imported. Submit it if it wasn't.

Inspect key URLs and review crawl or indexing issues.

Bing documents the import and verification process here.

Don't skip Bing just because you mainly care about Google. It matters for Bing and Microsoft's search experiences. ChatGPT search also works with third-party search providers. OpenAI names Bing in its Enterprise and Edu search documentation.

But Bing submission is NOT a direct ChatGPT registration. For ChatGPT search, also allow OAI-SearchBot and check that your host or firewall doesn't block its requests. OpenAI explains ChatGPT search eligibility here.

Run AI agent readiness and ask:

Check whether Googlebot, Bingbot and OAI-SearchBot can access our public pages. Review robots.txt and any available firewall or crawl evidence. Separate search access from model-training permissions. Report anything you cannot verify. Don't change bot rules without my review.

Checkpoint: verified Google and Bing properties, an accepted sitemap submission in each, and no known access blockers on your key pages.

Write, then make QA a hard gate

Run SEO blog writer for an approved blog brief. For a product or feature page, use the current Landing page writer.

Give your agent this prompt:

Write from the approved brief. Answer the question clearly, use verified product facts and add useful examples, internal links and a relevant next step. Flag missing screenshots or evidence. Save the draft. Don't publish it.

Give the reviewer this prompt:

Review this draft against its brief. Check facts, search intent, readability, original value, links, images and the call to action. Return specific fixes. Send failures back to the writer and recheck the final revision before it goes to publishing.

Publish and verify

Run CMS publishing adapter after QA passes.

Give your agent this prompt:

Turn this QA-approved draft into a CMS draft using our existing template. Check the title, URL, description, images, links, canonical and schema. Stop for approval. After approved publication, verify the live page, its sitemap entry and the actual content. Only then complete the task.

Start with one strong page and get this handoff working. Increase the pace when you can keep the quality.

Publishing 50 weak posts a day doesn't fix a weak strategy.

7. Measure customers. Improve the pages you already have.

Don't stop when a page goes live. This is where the system gets useful.

Search Console shows Google impressions, clicks and average positions. Analytics shows what visitors do after they land. You need both.

Set up a real conversion event, such as a completed signup, purchase or qualified enquiry. Test that it fires correctly. A click on “Sign up” is not the same as a completed signup.

Run SEO performance audit weekly once there is useful search data. Start with indexing and access checks while the site is new.

Give your agent this prompt:

Review our search performance and page-level conversions. Find pages worth improving, not just new topics to write about. Return a short task list with the evidence, proposed change and success measure. Don't draw big conclusions from tiny samples. Feed the useful findings into our next research run.

If you use PostHog, run PostHog change impact before a measurable change goes live.

Give your agent this prompt:

Pick the business outcome for this change, validate the tracking and save a baseline where one exists. Record the verified release date. Set up impact reviews after 7 and 14 complete days, with a later review if the sample is too small. Confirm whether scheduling is actually active. Keep search metrics in Search Console and visitor outcomes in PostHog.

Ask your agent to configure recurring research and audits using its scheduler. Check the saved schedule and first run. If your setup can't run in the background, use a weekly calendar reminder and run the same prompts manually.

The goal is a loop that learns:

Find a customer problem. Publish a useful answer. Measure what happens. Improve it. Repeat.
