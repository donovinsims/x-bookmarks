# How to Build Anything with Grok Bot (Full Course)

## Post

Most people open Grok Bot, spin up one bot, and hand it everything.
Research the market. Find a problem. Pick an idea. Write the code. Make the launch video.
Then they wonder why it starts mixing research with opinions and ships vibes instead of a product.
One bot doing ten jobs is the mistake. Ten bots doing one job each is the system.
Here's the setup I use: a small team of bots that finds a real problem, kills the weak ideas, writes the spec, builds the thing and scripts the launch, while I only make the decisions.

Why a team beats one mega-bot
Every bot in Grok Bot is a persistent teammate. Its own cloud computer, its own terminal and browser, files that are still there after you close your laptop, and the ability to run on a schedule.
That's exactly why narrow jobs work. Each bot stays in its lane:
the researcher never invents a business model
the analyst never designs pricing
the strategist never writes code
the builder never invents requirements that aren't in the spec
The thing that holds it all together isn't a smarter model. It's a handoff file.
 
The handoff file is the whole trick
Every week gets its own folder:
 
Each bot reads the file before it, writes its own, then adds one line to HANDOFF.md:
 
If it gets stuck, it writes BLOCKED and pings you instead of guessing.
Keep it in /workspace for a reason: that's the folder that survives when the bot's computer rebuilds itself. Anything outside it can disappear.
 
The weekly loop
Monday morning
 
Seven core bots. You touch it at two points: picking the pain, and approving the launch.
The shared rules every bot gets
Paste this block at the top of every bot's instructions. It's what keeps the team from going rogue:
- Work only inside /workspace/loop/, current week folder.
- Before starting, read HANDOFF.md. Only start when the step
  before you is DONE.
- When finished, write your file, then append to HANDOFF.md.
  If stuck, write BLOCKED + reason.
- Public pages and official APIs only. Respect rate limits.
  Never log into other accounts. Never collect personal data.
- Label every inference. Facts get a source link.
- Never post, publish, email, buy or delete anything without
  my approval in chat.
- Keep outputs short. Prefer tables.
That last rule matters more than it looks. The bots do the work, you keep the trigger.
 
Layer 1: find the problem
 
Scout runs every Monday. It scans Product Hunt, GitHub Trending, Hacker News, a few subreddits and public X posts, removes duplicates, and writes a ranked top 20 into trending.md. One flag worth asking for: products that are missing a platform people keep requesting. Mac-only tools with a comment section full of Windows users is a gap you can see without guessing.
Pain Miner takes the top 5 and collects public complaints: Product Hunt comments, HN threads, Reddit, GitHub issues. It clusters the negative ones into themes, ranks them by how often and how angry, and writes pain.md with real quote links. The rule that keeps it honest: never invent a quote. If something needs a login, skip it.
Competitor Mapper runs at the same time. For each product it finds 3 to 7 alternatives and builds a gap table: which needs nobody covers yet. If the pricing page is unclear, it writes "unknown" instead of making a number up.
By Monday afternoon you have evidence, not ideas.
Layer 2: decide if it's worth building
This is where most AI pipelines skip straight to code, and that's how you ship something nobody pays for.
Strategy Lead reads all three files and runs the idea through a few frameworks: what job the user is actually trying to get done, what to eliminate, reduce, raise and create versus competitors, and the hard Zero to One questions. Is it 10x better on something measurable, or just 10%? Why now? How do you reach users without praying to the algorithm? It ends with one recommended idea and a kill list.
CEO is the seat that stress-tests everything. Its job is to disagree. Challenge the premise, refuse to be agreeable, and end every review with GO, HOLD or KILL plus a 7-day experiment with a pass/fail number.
A clean kill on Tuesday is worth more than a finished product nobody wanted on Sunday.
 
Layer 3: build it
Spec Writer turns the winning idea into SPEC.md: the problem, the user, the platforms, what the product does on each input, edge cases, and acceptance tests written as Given/When/Then. Plus non-goals, written out explicitly, so the builder doesn't wander.
Builder only gets the spec. New project folder, open-source dependencies only, a test for every acceptance item, and a short report of what passed and what didn't. If the spec is unclear, it stops and asks you instead of inventing.
Video Director runs in parallel. It doesn't film anything. It writes the launch plan: hook in the first 5 seconds, problem, demo, CTA, a shot list, and a 15-second cut for X. Only your own product UI on screen, never someone else's.
A note on reverse engineering
The original version of this pipeline includes a bot that uses REA (Reverse Engineer Anything, github.com/morluto/rea) to study how an existing feature works before you rebuild it.
It's useful, but only inside clear lines. REA's own disclaimer limits it to software you own or are authorized to inspect. No DRM or license bypass, no copying proprietary code or assets. The safe pattern is clean-room: study what a feature does, write that behavior into SPEC.md, and build from the spec in a fresh context that never sees the original code.
If you're not sure you're allowed to inspect something, skip this bot. The pipeline works fine without it.
 
Routines: the part that makes it run without you
Grok Bot can run bots on a schedule, so the team doesn't need you to kick it off.
Monday 09:00: Scout runs the full scan and messages you the top 3
Daily: Pain Miner sweeps new complaints for the current top products
48 hours after launch: a review writes what moved, what didn't, and what Scout should look for next week
Keep the scans bounded. Public search has rate limits, so fewer, sharper queries beat spamming them.
What this can't do
Worth saying before you run it:
it can't see code that was never shipped to the client
distribution is still on you
the Strategy Lead and the CEO can both be wrong, you make the final call
trending numbers and hype posts are not proof something is easy to build
 
Your first weekend
Saturday: create the core bots, paste the shared rules into each, set Scout to run Monday morning.
Sunday: run Scout once by hand. Then Pain Miner and Competitor Mapper. Then Strategy Lead and the CEO. If you get a GO, write the spec and start the builder.
Next week: ship something small and run the 48-hour review.
One week from now you should have a folder of real evidence, a ranked list of problems, a strategy memo with a decision, and either a build or a clean kill. Not another pile of bookmarks.
The people building fast right now aren't the ones with a smarter model. They're the ones with a team, a spec, and a Monday routine.
