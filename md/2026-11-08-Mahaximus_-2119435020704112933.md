# Grok Bot Usage. Fix Everything That Burns Your Limit.

## Post

Most people hit their Grok Bot limit in the middle of the week and assume they need a bigger plan.

They don’t. Their bots are re-reading the same inbox every run, loading 40 tools to use 2, and checking for changes every 15 minutes on data that changes once a day.

None of that makes the work better. It just burns the week.

By the end of this article you will know where your usage actually goes and how to find the one bot eating most of it. You’ll also get the 7 leaks almost every setup has, with a fix you can paste for each one, plus a single prompt that handles all of them at once.

Where your limit actually goes

Most people think usage is the work: the bot writes an email, and that’s what costs something.

It doesn’t work like that.

Every time a bot runs, it reads everything it carries before doing anything: its instructions, the chat history, the definitions of every tool it has loaded, and every file and page it opens. Then it does the task. On the next run, it reads all of it again.

The task itself is usually the smallest part of the bill.

So usage comes from two things:

How often the bot runs. Every run pays the full reading cost again.

How much it carries into each run. Long chats, unused tools, whole files pasted in, and pages clicked through instead of fetched.

Your weekly usage is roughly those two multiplied together. Cut either one and the number drops. Cut both and it drops fast.

The good news is that almost none of that weight makes the output better. A bot that reads a 300-message chat history to answer one email doesn’t write a better email. It writes a more expensive one.

Find the culprit first

Before you fix anything, find out where the usage actually goes.

The catch is that Grok Bot only shows you one number: a weekly usage % for everything combined. It doesn’t tell you which bot spent it, or which routine.

It’s rarely spread evenly, either. A bot that quietly runs every 10 minutes looks harmless. A bot you talk to twice a day feels expensive just because you notice it.

Usually it’s a routine on a schedule far tighter than it needs, or a bot dragging a huge chat history into every run. Both are on the list below.

The Leaks

1 - Routines that run too often

This is the big one, and Cursor’s own help page for Grok Bot says it plainly. An hourly schedule, a short interval, or a Slack trigger on a busy channel “can use a week of usage in a day.”

Every run pays the full reading cost, so the schedule multiplies everything else.

Take an inbox bot that checks every 15 minutes. That’s 96 runs a day. If you get 6 emails a day, 90 of those runs find nothing and still pay full price.

The fix:

Match the schedule to the data. If the data changes once a day, run the routine once a day.

Use a trigger instead of a schedule where you can. A routine that fires when something happens doesn’t run when nothing does. Keep the trigger narrow, because a trigger on a busy channel fires constantly.

Batch. One run that handles everything new beats one run per item.

Pause what you don’t read. If you never open a routine’s output, it’s spending for nothing. A paused routine spends zero.

2 - Bots that re-read everything

Most routines start from scratch every run. The inbox bot reads the inbox top to bottom. The competitor bot reloads every page it watches. The report bot re-reads the whole sheet.

Run 50 does exactly the same reading as run 1, just to find the 3 things that changed.

The fix is a notebook. Your bots work on one persistent cloud computer with real files, and those files survive between runs. So keep a small file of what’s already been handled, and only process what isn’t on it.

One detail matters here: don’t use the bot’s memory for this. Grok Bot’s own docs say changing facts belong in the source system. Memory is for preferences and lessons, while a list of handled emails is state, and state goes in a file.

The fix:

Keep a “seen” file. It holds the IDs, links or timestamps of everything already handled.

Check it first. Every run starts by reading the file and only pulls items newer than the last run.

Write back at the end. Add what was handled and record the run time.

Cap it. Keep the last 30 days, so the notebook doesn’t become the new thing it re-reads.

3 - Context that never gets cleaned

This one comes straight from the Cursor team on their forum: every reply re-reads the bot’s whole conversation. It only summarizes itself when it gets close to the model’s limit, and there’s no compact button yet.

So a bot you’ve talked to for three weeks drags three weeks of chat into every reply. One user there reported around 200,000–250,000 input tokens per reply on a long-running lead bot.

The fix is to keep what matters somewhere the bot reads on purpose, and treat the chat as disposable.

Rules go in the profile, not the chat. Core instructions in the bot’s profile survive anything. A rule buried in message 40 doesn’t. Trim them while you’re there by cutting repeats and old rules.

Give each bot one brief file: who you are, what this bot does, your preferences, and the facts it keeps needing. The bot reads that first instead of digging through history.

Keep lessons, but cap them. After bigger tasks, the bot adds one line on what worked and what didn’t. Keep it to 20 lines, replacing old lessons instead of piling them up.

Start fresh when a chat gets heavy. Have the bot write a handoff summary into its brief, then Duplicate it. The copy keeps its profile, routines and skills but starts with an empty chat. Point it at the brief and hide the old one. The copy also starts with empty memory, which is why the brief file matters.

Send pointers, not dumps. Bots share files, so a specialist writes the full update to a file and sends the lead bot one line saying where it is.

4 - Tools loaded for no reason

Every plugin a bot has comes with a description of each tool inside it, and the model reads those descriptions so it knows what it can call. More plugins means more to read on every run.

Anthropic’s engineering team wrote this problem up last year. With enough tools connected, an agent can end up “processing hundreds of thousands of tokens before addressing a user request.”

Their fix was to stop loading every tool upfront. The agent finds the tool it needs when it needs it, and does the heavy data work in code instead of in the chat. On their example task, moving a meeting transcript from Google Drive into Salesforce, usage dropped from 150,000 tokens to 2,000. That’s 98.7% less.

That was Anthropic’s agent, not Grok Bot. But both ideas carry over, and Grok Bot gives you the controls for them.

The fix:

Turn off tools you don’t use. Grok Bot lets you switch connector tools on and off one by one under Settings -> Plugins. If a bot connected five apps for one job, it still carries all five.

Keep skills where they’re needed. Private skills can be enabled per bot, so don’t give every bot every skill.

Do heavy data in code. Big sheets, logs and inboxes get filtered on the bot’s computer, and only the rows that matter come back. A whole file never gets pasted into the chat.

Save what works as a skill. Skills work across all your bots, so a script that worked once never has to be figured out again.

5 - Browsing when a plugin exists

When there’s no plugin, Grok Bot works a website like a person: open the page, look at the screen, click, look again. Each of those steps is the model reading a page.

A plugin does the same job in one structured call. Gmail, Calendar, Notion, Slack and Drive all have one.

xAI’s own docs put it plainly: prefer a connector when one is available, because it’s often more reliable than clicking through a website. Fewer steps usually means less usage too.

There’s a hidden cost as well. A bot can run only one browser task on its screen at a time, so a bot stuck clicking through a site can’t do anything else.

The fix:

Check what your bots browse. Any site a routine visits regularly is a candidate.

Connect the plugin if one exists (Settings -> Plugins -> Add), and tell the bot to use it for that job.

Keep the browser for what plugins can’t do: sites with no plugin, or visual steps the plugin doesn’t expose.

Check the plugin’s own cost. Some plugins bill separately. The X plugin, for example, needs X API credits on your developer account.

6 - Bots doing the same work

Once you have more than a few bots, they start stepping on each other. Two bots watch the same inbox. The lead bot reads every incoming item just to decide who should handle it. Work bounces between bots, and every bounce is another full run.

None of that shows up as one obvious problem. It’s a tax on every task.

The fix:

One owner per job. Every source and every task type gets exactly one responsible bot. Write it down in one roles file that every bot can read.

Cap the handoffs. A job can move between bots at most 3 times. If it isn’t done by then, it comes to you instead of bouncing forever.

Make routing cheap. Deciding “who handles this?” doesn’t need your lead bot reading its whole history every time. That’s what Jev is for.

Jev is a decision model from TypeSafe AI. It doesn’t write text. You give it a situation and a typed question, like “which of these roles owns this?” or “how urgent is this, 1 to 5?”, and it returns the answer with a confidence score.

TypeSafe claims up to 194x faster and 445x cheaper than frontier models, on its own workflows. Independent tests came in lower, around 5–10x faster and 4–6x cheaper. That’s still a big gap for something your bots do on every single item. Jev bills separately, through its own API.

7 - Loops that never stop

A loop is a bot that keeps working until the job passes: try, check, fix, try again. It’s the most powerful thing a bot can do, and the most dangerous for your usage. A loop with no exit doesn’t stop when it’s stuck. It stops when your week runs out.

The usual suspects:

A retry that can’t succeed: a login the bot can’t pass, a page that won’t load, a check that will never go green.

Two bots reviewing each other’s work back and forth. One thread on Cursor’s forum is titled “weekly usage hits 100% after bot-to-bot reviews the user asked to stop.”

A routine that keeps spawning follow-up work that spawns more work.

The fix:

Give every loop a real finish line. “Done” means a check passes, not that the bot feels finished.

Cap the tries. After a set number of attempts, it stops and reports what failed.

When stuck, report instead of retrying. The same error twice in a row means stop and tell you.

Know your off switches. xAI’s docs say to send the bot a direct “Stop now” message. Also set a hard cap on extra usage, so a loop can’t keep spending after your week runs out.

When not to bother

Not every bot is worth optimizing. Before you spend an evening on this:

Skip bots that barely run. A routine that fires once a week isn’t where your limit goes. Start with whatever the detective ranks first.

Never trade the work for the tokens. If a cheaper setup misses emails or writes worse drafts, it isn’t cheaper, you’re just paying in a different place. Undo it.

Don’t trust savings you didn’t test. Estimates are where you start. The 24-hour pause and your weekly % are the proof.

Some weeks are just heavy. A big project burns more usage, and that’s fine. This is about waste, not work.

What you now have

Your weekly limit isn’t eaten by the work. It’s eaten by everything around it:

routines running more often than anything changes

bots re-reading what they already handled

chats that never get cleaned

tools loaded for jobs that don’t need them

websites clicked through when a plugin was right there

bots doing each other’s jobs

loops with no exit

Each one has a fix, and none of them makes the work worse. A bot carrying less has less to get wrong.

My take: don’t start with the fixes. Start with the detective prompt tonight. One bot is eating your week, so find it, fix that one, and watch what happens to your %.

The rest can wait.
